# 自主测试闭环方案 —— 新功能冒烟（写案例→执行→截图→读图→判断→修→再验）

> **日期**：2026-07-27。**状态**：待确认后开工。
> **目标**（用户原话）：借鉴 Claude Code 形成自主测试闭环——Agent 自主写测试案例、写脚本、截图、多模态读图、判断、修改代码，循环到通过。
> **CC 出处**：verification agent 动作库与证据契约（`verificationAgent.ts`）、claude-in-chrome 截图纪律、`/plugin install playwright` 的"screenshot what it built, and fix visual bugs itself"（`commands/init.ts:220`）、verifier 的"execute the plan EXACTLY as written"（`init-verifiers.ts:181`）。详见 `external/claude-code-测试手段借鉴.md`。

## 0. 闭环全貌（六步一循环）

```
实现分片交付 ──► ①写冒烟单(案例) ──► ②验证棒按单执行(脚本)
      ▲                                    │
      │                                    ▼
      │                            ③逐步骤 browser 截图
      │                                    │
      │                                    ▼
      │                       ④截图喂回模型读图判断(多模态)
      │                                    │
      │                                    ▼
      │                ⑤console断言(机判)+读图判断(模型) → VERDICT
      │                                    │
      └──────── ⑥不过:证据(报错+截图+判断)回灌修改代码 ◄──┘
                                    │
                                    ▼
                          全过 → VERDICT: PASS → 冒烟单+截图归档沉淀
循环上限 3 轮,熔断转人工(复用交棒熔断思想)
```

## 1. 六步拆解（每步：做什么 / CC 参照 / BH 现状）

### ① 写冒烟单（写案例）
- **做什么**：实现分片交付 = 代码 + 冒烟单（入口/步骤/断言/预期）。交付契约强制：**没冒烟单 = 没交付**（进诚信四条同款判据）。
- **CC 参照**：verification agent 分类型动作库（前端/后端各有命令链）；init-verifiers 的"验证计划"。
- **格式**（弱模型填空式，不许自由发挥）：
  ```
  【冒烟单】功能:<名字>
  入口:<URL 或 接口>
  步骤:① <打开/调用> → <预期>;② <操作> → <预期>;③ <操作> → <预期>
  断言:console 无错误;无 4xx 资源;<业务断言:最终页/响应含 X>
  证据:截图路径(前端) / 响应原文(后端)
  ```
  后端同款：接口+正常参数→预期字段+异常参数→预期错误。
- **BH 现状**：没有——本轮新做（交付契约进 window.js 编码规程 + 验证棒提示词）。

### ② 按单执行（写脚本+跑）
- **做什么**：验证棒拿冒烟单逐条执行（browser_navigate/click/type/eval 或 curl）。**写代码的不许自己验**（新眼睛）。
- **CC 参照**：verifier "execute the plan EXACTLY as written"（`init-verifiers.ts:181`）。
- **BH 现状**：工具面全齐，只需写进验证棒提示词。

### ③ 逐步骤截图
- **做什么**：每个关键步骤后 `browser_screenshot`，路径记入证据。
- **CC 参照**：claude-in-chrome 的 gif_creator 多步留帧思想（`prompt.ts:7-11`）。

### ④ 多模态读图判断（本方案的灵魂步骤）
- **做什么**：验证棒 **read 截图文件**（serve 的 read 工具把图片当 base64 附件返回——模型直接拿到图）→ 问模型："这是<功能>的页面，判断：布局破没破？内容对不对？是不是白屏/报错页？哪不对？"
- **为什么必须这步**：console 断言只能查"没报错"，查不了"长得不对"（布局崩/内容错/样式裸奔）——**视觉正确性只有读图能判**。
- **BH 现状**：session.js 已有多模态切换（消息带图自动找 image 模型）。**风险点**：内网模型可能无多模态——降级为"console + DOM 文本断言"（browser_get_text 对照预期文案），提示词里写明降级路径。
- **CC 参照**："screenshot what it built, and fix visual bugs itself"（`init.ts:220`）。

### ⑤ 双路判断 → VERDICT
- **做什么**：console 断言（机判：无 error/无 4xx/非白屏）+ 读图判断（模型：长得对不对）双路都过才 PASS；输出仍按 VERDICT + Command run 契约（机判已有）。
- **BH 现状**：VERDICT 机判已上线（db6a880），判断条件加"读图结论"一条。

### ⑥ 不过就修，循环到绿
- **做什么**：FAIL → 证据包（报错原文 + 截图路径 + 读图判断 + 冒烟单）回灌实现分片修复 → 修完再走 ②-⑤；循环上限 3 轮熔断转人工。
- **CC 参照**：主 agent 契约"FAIL 则 fix, resume the verifier, repeat until PASS"（`prompts.ts:394`）。
- **BH 现状**：失败按写归属回派的通道已有（验证棒目标文本自带），加循环计数与熔断。

## 3. 明确边界

- 多模态是**增强不是前提**：内网无多模态时，闭环照跑（console+DOM 断言），只是少了"看图"那一路；探针（C3）确认后自动启用。
- 回归测试（录制回放）不在本方案：那是"旧流程别坏"，本方案管"新功能冒烟"；冒烟单归档后是半回归资产，与录制库互补。
- 后端闭环同款（curl 执行+响应判读），无截图与读图环节。
