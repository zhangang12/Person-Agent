# 内网引擎需求 —— 上下文工程（bocomcode fork）

> 给 bocomcode（opencode 内网 fork）引擎侧的需求清单。背景：128k 上下文窗口（MiniMax M2.5）下，编码/转换类任务的"读原文"是刚性消耗——三四个大文件（80–100KB/个）就能吃掉 70–90% 上下文，"还没读完就触发压缩"是实测现象。壳层（BocomHermes）已做了纪律注入/字节计量纠偏/分片隔离/主动交棒，但**工具输出在 serve 内部进上下文，壳层无法截断**，以下三项只能在引擎侧做。按 ROI 排序。

## R1 工具输出截断（最高优先级）

**问题**：内建 read/grep 工具输出无截断（或截断线过高），单次 read 可进数万 token。弱模型不带 offset/limit 直接全量读。

**需求**：
- read 工具：默认最多返回 400 行（可配置），超出时在结果尾部追加 `…(共 N 行,已截断至 400 行;用 offset/limit 继续读)`；单行超 2000 字符截断该行。
- grep 工具：默认最多返回 200 个匹配（可配置），超出注明总数。
- 截断阈值走配置（opencode.jsonc 或环境变量），不要写死。

**验收**：对 3000 行文件直接 read，进上下文的 ≤400 行且带截断说明；模型能用 offset 读完全文。

## R2 历史工具结果清理（tool result clearing）

**问题**：长任务里历史深处的工具输出（几十轮前读过的文件内容）基本不会再被用到，但每一轮都在付上下文账，还加剧 Context Rot（性能随长度非均匀下降）。

**需求**：会话内自动清理——只保留最近 N 轮（建议 N=3，可配）的工具结果全文，更早的工具结果替换为占位符（如 `[工具结果已清理:read <path>,原 12000 字符]`）。Anthropic 平台已把同款能力做成官方特性，可作为语义参照。

**验收**：50 轮长会话中，第 10 轮之前的工具结果全文不进模型输入；模型近期轮次的工具结果完整可用。

## R3 缓存断点（KV-cache breakpoint）

**问题**：Agent 输入:输出 token 比约 100:1，缓存命中与否是 10 倍成本差。serve 若不支持手动 cache 断点，长 system prompt 的缓存收益拿不到。

**需求**：支持在消息上标记 cache 断点（至少覆盖 system prompt 末尾）；并保证会话历史序列化确定性（JSON key 顺序稳定），不因实现细节破坏前缀缓存。

**验收**：连续两轮请求，第二轮的 prompt 前缀缓存命中率 ≥90%（可在日志暴露 cache_hit 统计）。

## 兼容性确认项（非需求，是问题）

1. fork 是否保留了 opencode 的插件机制（oh-my-openagent 在内网能用说明大概率在）？插件的 `tool.execute.after` 类钩子能否**修改**工具输出？——若能，R1 可由壳层插件实现，不必动引擎。
2. fork 的 read 工具现状：有无截断、阈值多少？（决定 R1 是"加"还是"调"）
3. serve 是否暴露会话级真实 token 用量（壳层 ctx chip 已消费该数据，确认长期兼容）。
